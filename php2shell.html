PHP2Shell: CVE-2026-109618 & CVE-2026-109619

Pre-patch intelligence brief for SOC and threat hunting teams. Two critical PHP remote-code-execution flaws, an embargo that broke roughly 22 hours before the fix, and exploit code already in public circulation.

Bottom line

  1. Two PHP core RCEs, rated CVSS v4.0 9.2 each by the PHP security team. Fixed versions are reported as 8.5.12, 8.4.27, 8.3.36, 8.2.35. None of that is confirmed by PHP yet — the advisory ships today at 14:00 UTC.
  2. No confirmed exploitation in the wild, no IOCs, not in CISA KEV. watchTowr and Huntress both report nothing observed as of this writing. That is a statement about their telemetry, not proof of absence.
  3. Exploit code is public, but the headline PoC is self-discounting. A 39.7 MB "lab weaponized" bundle has been downloadable since ~01:58 UTC and was re-uploaded at 03:24; thirty-five GitHub repositories now exist, most of them defensive. The author's own ASAN build armed both cached pointers and did not fire a use-after-free — the crash needs a heap-groom stage the bundle does not demonstrate. The pre-patch exposure window is now ~17 hours old.
  4. The root cause is genuinely contested. Five incompatible technical models are circulating, the newest arriving at 13:35 UTC — and one of them is the leaker's own. One is a heap use-after-free requiring a per-build offset leak; another is a session state-machine chain that only reaches RCE through an application-level include(); a public php-src pull request matches one primitive exactly; the fourth moves the use-after-free into PHP's unserializer entirely. Do not plan on the headline version.
  5. Act now on inventory, not on the exploit narrative. Patch internet-facing PHP at 14:00 UTC, treat PHP 8.1 and older as permanently exposed, and hunt on process lineage plus session-file content rather than on request signatures.
  6. There are no network IOCs. The IOC is a host artefact. Nothing connects to an external address — the only URL in the published bundle is a https://host/x.php placeholder. The durable signal is a session file containing upload_progress_<?php. The published User-Agents and the t[] groom shape belong to one tool and change in seconds.

Technical assessment

Five competing models, none of them vendor-confirmed

Every public description agrees the flaw is reachable through multipart/form-data against a PHP endpoint with session.upload_progress enabled — which is the default. Beyond that, the accounts diverge sharply, and the difference matters enormously to impact.

Model A — heap use-after-free in the upload-progress callback

Published by J4ck3LSyN (ATLAS) with research credits to Andrew Dorman and Arch&Yuki, and mirrored by at least one GitHub repository. It claims php_session_rfc1867_callback caches two raw zval * bucket pointers (post_bytes_processed, current_file_bytes_processed) that are invalidated when the session tree is freed and rebuilt on a second progress update. The stale pointer is shaped into a fake zend_fcall_info, reaching zend_call_function and then system().

Its own page undercuts the strongest reading: it requires a per-build offset leak between zval_ptr_dtor and zend_call_function, ships three vendor debug-symbol files to derive it, and describes itself as "weaponized (lab)". Unconfirmed (source)

What the bundle's own validation says — and what we could verify

The bundle now carries VALIDATION.md, REPORT_VALIDATION.md, RATING.md and DELTAS_LSphp.md. They describe two bugs (a stale read through post_bytes_processed and a stale store through current_file_bytes_processed) and cite exact source lines rather than prose. The document labels itself "conceptually validated … ASAN reproduction in progress"; the page's section 7 then reports that reproduction: the 258-byte multipart request reached the vulnerable path and armed both cached bucket pointers, but no ASAN heap-use-after-free fired. The author's explanation is that the freed chunk must first be reclaimed as an attacker-shaped 149-element packed array, and that grooming stage is not in the bundle.

We checked the source claims independently against the php-src PHP-8.4 branch at 06:45 UTC. All twelve cited lines match what the tool describes — the two cached zval * fields at php_session.h:136–137, the zend_hash_str_find captures at session.c:3316/3342, the stores at :3355/3356/3375, the zend_hash_update at :3214, min_freq at :953, and FILLUNIT 5120 at rfc1867.c:184. We also confirmed the disputed Z_TRY_ADDREF(progress->data) at session.c:3213, one line before that zend_hash_update — the addref the independent 04:38 audit says prevents the tree from being freed at all. Source reading: accurate. End-to-end exploitation: still not demonstrated by anyone.

Model B — session and multipart state-machine flaws

A second repository documents five primitives verified against php:8.4.4-cli in a local Docker instance and explicitly states that Model A's "two-update UAF" is "mechanically falsified" — nothing in its chain touches a dangling pointer. Its primitives:

  • P1 — a multipart form field named PHPSESSID is accepted before script resolution, creating sess_<attacker-chosen-id> even with session.use_only_cookies=On and no Cookie header.
  • P2 — the PHP_SESSION_UPLOAD_PROGRESS value is stored verbatim as a session key and re-serialized into the session file, so attacker-chosen content lands on disk.
  • P3 — corrected at 07:00 UTC. The original claim was that exceeding max_multipart_body_parts skips the cleanup event, leaving the poisoned file behind. It does not: the bail path does goto fileupload_done (rfc1867.c:797) and MULTIPART_EVENT_END fires there unconditionally (:1268–1273). With stock cleanup=1 the progress entry is therefore deleted and the session file ends up empty. The 19h repository has reached the same conclusion in its own README ("CORRECTED MODEL", cleanup=0 → 556 B, cleanup=1 → 0 B) while its report file still states the opposite. Treat session.upload_progress.cleanup=0 as a hard prerequisite for this chain. Verified in source by us.
  • P4/P5 — session fixation with attacker-chosen values, and a silent write-denial when the marker contains |.

RCE in this model needs an application-level code-execution sink — an include()/require() of a session-mapped path, or unserialization of attacker-controlled session values. That is a materially narrower claim than "unauthenticated RCE on any PHP host". Medium — locally reproduced, not independently audited. (repository)

Model C — the missing cookie-only guard, already public since May

php-src PR #22113, opened 2026-05-21 and still open, adds exactly the guard Model B's P1 describes: php_session_rfc1867_early_find_sid() already honoured use_only_cookies for $_GET, but the form-field capture in MULTIPART_EVENT_FORMDATA had no such check. The pull request adds a four-line check and a rfc1867_sid_post_use_only_cookies.phpt test.

Its author wrote, in the pull request itself: "I don't know if this is a security fix." It has been reviewed and reworked but never merged. This predates the leak by five months and is the single strongest corroboration that at least one of the two flaws is a session-handling logic bug rather than memory corruption.

Re-checked 06:41 UTC: still open, merged: false, last updated 2026-10-16, 9 comments and 2 review comments, head branch jorgsowa:fix/session-upload-progress-use-only-cookies targeting PHP-8.4. Unchanged since the leak — if this were the fix, it would have been merged by now.

Analytic inference — not a published finding

Two CVE identifiers for what several sources describe as one disclosure is easiest to explain as two distinct issues: one memory-safety bug and one session/multipart logic bug. Nothing public confirms that split, the mapping between IDs and issues is ambiguous in every circulating source, and the jackalsyn bundle never says which ID is which. Treat the pairing as unresolved until 14:00 UTC.

Revised 09:10 UTC: a third candidate now exists for the memory-safety half — the unserializer reentry described above, rather than the session callback. The "one memory bug, one logic bug" shape survives; which memory bug does not. That is one more reason not to build detections on a specific primitive before the advisory lands.

What this means for your risk assessment

If Model A is correct, internet-facing PHP is directly exploitable and the 9.2 score is conservative. If Model B is correct, mass exploitation depends on how many applications include session paths — far fewer than "all PHP", but the session-fixation primitive alone is still a credential-theft problem on nearly every PHP application. Plan for the worse case, but do not tell leadership that every PHP server is a guaranteed shell.

A fourth chain, outside session.c — checked 09:00 UTC

At 07:55 UTC a repository appeared claiming three independent RCE chains, the memory-corruption one located in PHP's unserializer rather than the session handler: ikow/php2shell-poc, by Qi Deng. The author has prior published work on React Server Components RCEs, which earns a read rather than a dismissal — so we read it, and then we read the code it describes.

The mechanism, taken from PHP-8.4 in our own tree:

  • var_destroy() frees the back-reference var_entries chunks first (var_unserializer.re:242–246), then walks the delayed-destructor list and calls i_zval_ptr_dtor() at :308. Unlike the __wakeup and __unserialize invocations at :277 and :294, that destructor call is not bracketed by BG(serialize_lock).
  • With the lock down, a unserialize() issued from inside __destruct takes the reuse branch of php_var_unserialize_init() (:77–80) and is handed the in-flight parser state — the exact structure whose back-reference chunks were freed a moment earlier.
  • The inner parse then runs var_push() against ->last, which still points into the freed chunk: :118 reads it and :132 writes data[used_slots++] through it. That is a use-after-free write, not merely the stale read the author's back-reference trigger demonstrates.
Assessment — a real defect, at the wrong size

Source confirmed the ordering, the missing lock and the reuse branch are exactly as described. We did not execute anything: this environment has neither a PHP binary nor a container runtime, so the author's ASAN trace remains Unreproduced here.

Long-standing, therefore unlikely to be new the same reuse logic is present verbatim in PHP-7.2 (:37) and PHP-8.2 (:63). A defect shipped for years, in a path every object-carrying unserialize() traverses, is an odd candidate for a freshly assigned critical — whatever it is filed under.

Not a pre-auth core RCE all three of the repository's chains need something from the application: an include() of an attacker-influenced path, an unserialize() of attacker-controlled data with classes permitted, or a per-directory session.serialize_handler mismatch plus a POP gadget. That precondition is the one the earlier models already carried, restated as though it were new.

The escalation is asserted rather than shown — reading zif_system out of executor_globals.function_table and rewriting var_dump's handler through /proc/self/mem. The write step presupposes code execution the chain has not yet obtained, and the ASLR position is never explained. Treat the whole thing as a Medium lead against a Unconfirmed CVE mapping. Note also that the README's "full writeup" link points at a Substack whose newest post is dated 19 October and is not about PHP — as of 09:00 UTC the only copy of this analysis is the repository itself.

Model E — the leaker's own root cause, in zend_interfaces.c — checked 13:35 UTC

This one matters more than its position in the list suggests, because of who published it. The @calif_io account that dropped the PHP2Shell claim and the exploit video on 20 October also published a technical write-up and PoC under the label MADBugs. It locates the bug somewhere none of the other four models do: Zend/zend_interfaces.c.

The claim is a one-line omission. zend_user_unserialize() dispatches the userland Serializable::unserialize() method, and unlike the __wakeup and __unserialize dispatch points in var_unserializer.re (:277, :294, both verified in this brief), it does not raise BG(serialize_lock). With the lock at zero, an inner unserialize() called from inside that method shares the outer parser's back-reference table; the inner object's property zvals get registered as outer slots pointing into its own property-table buffer; a later property-table resize frees that buffer; and an R:N back-reference then reads through the stale slot.

What we verified, and what it implies for the CVE mapping

Source confirmed zend_user_unserialize() at zend_interfaces.c:442–461 contains no BG(serialize_lock) increment — the string does not appear anywhere in that file — and the function is byte-for-byte equivalent in PHP-8.2 at :438. The asymmetry with the __wakeup/__unserialize paths is real.

But it is probably not either CVE. The write-up assigns no CVE identifier, and it notes PHP's standing 2017 policy that unserialize() memory-corruption bugs are not treated as security vulnerabilities. If that policy still holds, a 9.2 advisory is unlikely to be this. The likelier reading is that the leak bundled two different things: the session-handler CVEs that PHP is actually patching at 14:00 UTC, and a separate unserializer UAF that the leaker had also found and demonstrated.

Reproduction is claimed, not witnessed — 10/10 local runs on PHP 8.5.5, and 3/3 remote against php:8.5-apache at roughly 2,375 HTTP requests per run. We have not reproduced it and cannot: no PHP runtime here. The remote precondition is genuinely strong — the target must load a Serializable class that recursively deserializes inner data and then enlarges the inner object's property table. The write-up itself calls real-world matches "uncommon".

Detection and hunting

Hunt the effect, not the request

Request-level signatures are weak here. The exploit path is a well-formed multipart POST to a legitimate endpoint, TLS hides most of it, and the progress-field marker is trivially varied. What does not vary cheaply is what happens next: PHP spawning a shell, and PHP writing code into a session file.

Signal 1 — process lineage (highest value)

Any web-server user spawning a shell, a downloader, or an interpreter is worth a look. Expect this to be noisy in shared-hosting and control-panel estates; run it in observe mode first and baseline for a day.

# auditd / EDR equivalent — parent is a PHP SAPI
(parent_process_name IN ("php-fpm","php-cgi","php-cgi.exe","httpd","apache2"))
AND process_name IN ("sh","bash","dash","zsh","curl","wget","nc","ncat",
                     "python","python3","perl","cmd.exe","powershell.exe","certutil.exe")
Generic lineage predicate
DeviceProcessEvents
| where InitiatingProcessFileName in~ ("php-fpm","php-cgi","php-cgi.exe","httpd","apache2")
| where FileName in~ ("sh","bash","dash","curl","wget","nc","python","python3",
                       "perl","cmd.exe","powershell.exe","certutil.exe")

Microsoft Defender XDR (KQL)

Signal 2 — PHP code inside a session file

In Model B this is the durable artefact: a session file containing an upload_progress_<payload> key. It survives request death only when session.upload_progress.cleanup=0 — the multipart parse bail still fires the cleanup event. This should be near-zero in a healthy estate, but legacy applications do occasionally store markup in sessions — baseline before alerting.

# find session files whose content contains a PHP open tag
grep -rl --include='sess_*' '<?php' /var/lib/php/sessions /tmp 2>/dev/null

# files owned by the web user, written in the last 24h
find /var/lib/php/sessions -name 'sess_*' -mtime -1 -user www-data -type f
Host hunt — read-only

Signal 3 — the in-band warning

The lab reproduction produced a distinctive start-up warning class. If it appears at volume against one vhost, that is worth escalating:

PHP Request Startup: ... in Unknown on line 0
Log string, lab-derived

Signal 4 — request shape (only where TLS terminates)

A multipart body carrying both a form field named PHPSESSID and a PHP_SESSION_UPLOAD_PROGRESS value containing <?php is the shape to look for. Correlate with the absence of a session cookie, and with multipart bodies that abort or exceed the configured part limit.

Action plan

What to do before, at, and after 14:00 UTC

Now — the seven hours before the patch

  1. Inventory PHP by version and SAPI, not just by hostname. Include php-fpm, mod_php, php-cgi, appliances, cPanel/Plesk, and Windows software bundling php-cgi.exe. Record which branches are already end-of-life.
  2. Verify the effective configuration, not the file. session.upload_progress is typically on by default. On Debian/Ubuntu, CLI and FPM read different ini paths, and .user.ini is cached for minutes. Check via phpinfo() or the FPM binary and reload the pool.
  3. Pre-stage the patch. Confirm repository or mirror access for 8.5.12, 8.4.27, 8.3.36, 8.2.35 and test in staging. Distributions may backport rather than rebase — check your vendor's advisory separately.
  4. Enable the lineage detection in observe mode and baseline the session directory today, so tomorrow's alert has something to compare against.
  5. Do not run the circulating bundle. Hash mismatch, plain HTTP, and no independent audit.
  6. Consider OS-level containment while you wait. An AppArmor or SELinux profile that stops the PHP SAPI from executing binaries blunts both models whichever root cause turns out to be right — and it is the only control that covers EOL branches you cannot patch. It matters most for vendor appliances shipping PHP without a mandatory-access-control policy.

At 14:00 UTC — when the advisory lands

  1. Read the official advisory first, then correct every assumption in this brief: affected versions, fixed versions, root cause, and which CVE maps to which issue.
  2. Patch internet-facing first, then internal. Restart the correct SAPI — a package upgrade alone does not always reload a long-running FPM pool.
  3. Decide explicitly on EOL branches. PHP 8.1 and older get no fix. The option set is upgrade, isolate behind VPN or allowlist, or accept the risk in writing. Doing nothing is a decision; make it a documented one.

After — the retrospective hunt

  1. Hunt back to 20 October 15:20 UTC, when the identifiers became public, and to 21 October 01:58 UTC, when the bundle became downloadable.
  2. Check the two artefacts that survive: session files containing <?php, and web-user processes spawning shells.
  3. Watch CISA KEV. A listing would convert every unpatched host from a priority into a deadline.
  4. Do not treat the upload_progress stopgap as protection. The sources now split three ways: the bundle author says it closes one of two paths; break-the-build says lab testing showed it closes the entire vulnerable path; GMO Flatt Security states it "mitigates only" and the attack remains possible, patch is the fix. Where vendors disagree about a free control, assume the pessimistic reading and patch.
If you can only do one thing today

Produce the list of internet-facing hosts running PHP 8.1 or earlier. That list is the part of your estate no patch will ever fix, and it is the part a mass-exploitation campaign would find first.
